가격 정합성을 지키는 여섯 가지 핵심 설계

공고에서 가장 중요하게 언급된 「거래처별 가격 · 최소 주문 수량 · 견적→주문 흐름」에 대해, 각 요구를 어떤 구조로 구현하는지 정리했습니다.

설계 ①
거래처별 공급가 · 할인율 — 3단 조회

모든 가격 조합을 하나의 테이블에 미리 생성하지 않고 ① 상품 기본가 → ② 등급 할인율 → ③ 거래처 개별 단가의 3단으로 둡니다. 조회 시 ③이 있으면 ③, 없으면 ①에 ②를 적용합니다. 전 조합 150만 행을 만들지 않고 실제 등록된 예외만 저장합니다.

설계 ②
해당 거래처에게만 보이는 가격

상품 조회 API가 로그인 토큰에서 거래처 ID를 추출해 조회 조건에 강제로 적용합니다. 클라이언트가 전달하는 거래처 ID는 조회 기준으로 사용하지 않습니다. 타사 가격을 요청하면 서버가 접근을 차단하고 감사 로그를 남깁니다.

설계 ③
주문 시점 가격 확정 — 스냅샷

견적 확정·주문 생성 시점의 단가·할인율·수량·공급가·부가세·합계를 그 행에 스냅샷으로 복제 저장합니다. 이후 모든 조회·통계·세금계산서 정보는 마스터가 아닌 이 스냅샷만 읽습니다. 단가 마스터는 변경 이력(누가·언제·얼마에서 얼마로)을 별도 테이블에 남겨 두 방향에서 증명합니다.

설계 ④
장바구니에 담은 뒤 단가가 바뀐 경우

장바구니 행에 담은 시점의 단가를 함께 저장해 두고, 주문 확정 직전에 현재 단가와 대조합니다. 차이가 있으면 변동 품목을 행 단위로 고지하고 재확인을 받은 뒤에만 주문이 생성됩니다. 거래처가 모르는 사이에 금액이 바뀌는 경로를 없앱니다.

설계 ⑤
최소 주문 수량(MOQ) · 주문 단위

상품마다 MOQ와 주문 단위(예: 12개 단위)를 두고, 장바구니 담기 · 주문서 작성 · 최종 주문 확정의 3지점에서 검증합니다. 장바구니 저장 후 관리자가 MOQ를 상향한 경우도 최종 확정 단계에서 감지하며, 기준을 충족하지 못한 품목과 사유를 행 단위로 표시합니다.

설계 ⑥
견적 → 주문 전환

전환 시 견적 행을 주문 행으로 복제하고 원본 견적 번호를 남깁니다. 전환 과정에서 가격을 다시 산정하지 않으므로 견적 확정 시점의 금액과 수량이 주문에 그대로 유지되며, 주문 상세에서 근거 견적을 역추적할 수 있습니다.

네 가지 요구를 하나의 구조로 「주문 시점 가격 확정」·「견적→주문 금액 일치」·「기간별 매출 통계의 불변성」·「세금계산서 정보의 정확성」은 주문 행 스냅샷을 공통 기준으로 삼습니다. 스냅샷으로 금액을 고정하고, 견적 번호 역추적으로 근거를 남기며, 통계와 세금계산서 정보도 같은 원천 데이터를 사용해 네 영역의 정합성을 일관되게 유지합니다.
